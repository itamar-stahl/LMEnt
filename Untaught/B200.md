# Running on the B200 cards

The cluster has sixteen B200s across `n-b200` and `n-b201` that this project could
not use at all, and the reason was one line of a package listing rather than
anything about the hardware. This is what the block was, how it was removed, and
what the resulting environment has and has not been shown to do.

## What blocked it

A job submitted to `gpu-b200-killable` with the `lment` environment dies about six
minutes in:

    RuntimeError: CUDA error: no kernel image is available for execution on the device

B200 is Blackwell, CUDA compute capability 10.0. The `lment` environment ships
`torch 2.6.0+cu124`, and a CUDA 12.4 build carries kernels for

    sm_50  sm_60  sm_70  sm_75  sm_80  sm_86  sm_90

which stops one generation short. PyTorch says so itself on stderr, and
`torch.cuda.get_arch_list()` confirms it from inside the environment. Nothing in
a training config reaches this: no `constraint`, `partition` or microbatch
setting adds kernels to a prebuilt wheel.

The driver is not the problem. `nvidia-smi` on `n-b200` reports driver
`595.71.05`, advertising CUDA 13.2, so the node will run any CUDA 12.8 or 13.x
build. The only thing that had to change was the wheel.

One trap to know about: `run_environment.json` records
`"triton_compilable": true` for these cards, because `adapt_to_gpu` decides that
from `capability >= 7`. That says nothing about whether kernels exist for
`sm_100`, so the run's own record looks healthy right up to the point it dies.

## The environment

    /home/dcor/galbarak2/conda_envs/lment-b200

Built from OLMo-core's declared dependencies rather than from `environment.yml`.
The yml pins `torch==2.6.0`, `triton==3.2.0` and the whole `nvidia-*-cu12==12.4.*`
family -- precisely the versions that have to change -- while `pyproject.toml`
asks only for `torch>=2.5.1` with no upper bound. Building against the looser,
truthful constraint is far less work than fighting several hundred exact pins.

    python 3.12 · torch 2.11.0+cu128 · triton 3.6.0
    numpy 1.26.4 · transformers 5.15.0 · ai2-olmo-eval 0.5.0
    omegaconf 2.3.1 · safetensors 0.8.0

    arch list: ['sm_75', 'sm_80', 'sm_86', 'sm_90', 'sm_100', 'sm_120']

`numpy` stayed below OLMo-core's `<2.0` cap on its own, and `ai2-olmo-eval==0.5.0`
installed without dragging a cu124 torch back in.

**This environment cannot run on TITAN Xp or V100.** Its arch list starts at
`sm_75`, so `sm_61` and `sm_70` are out. It is an addition beside `lment`, not a
replacement: anything on `studentkillable` still needs the original.

## Using it

`framework/env.sh` already makes all three knobs overridable, so no code changes:

    export ANACONDA_ROOT=/home/dcor/galbarak2/anaconda3
    export CONDA_ENVS_PATH=/home/dcor/galbarak2/conda_envs
    export CONDA_ENV=lment-b200
    . ./activate_env.sh

In the config, name the partition and leave the constraint empty:

    partition: "gpu-b200-killable"
    constraint: ""

Empty matters for two reasons. The partition contains only B200 nodes, so a
constraint adds nothing; and `job.constraint` is *not* in `RESUME_IGNORED_FIELDS`
-- it is in `RESUME_EMPTY_MATCHES_ANY`, where an empty value matches anything but
two different non-empty values are deliberately different experiments. Writing
`constraint: "b200"` on a run continuing an `h200` run silently starts from
random init instead of resuming. That mistake cost 11,500 steps once already.

## What it measured

A 50-step run at the standard 1B config -- 131,072-token global batch, 16,384
rank microbatch -- on four B200s, against the same config measured on H200:

| | GPUs | s/step | one epoch (27,416 steps) | GPU-hours |
|---|---|---|---|---|
| H200 | 4 | 2.54 | ~19.3 h | 77.4 |
| H200 | **1** | **2.30** | **~17.5 h** | **17.5** |
| B200 | 4 | 1.39 | ~10.6 h | 42.4 |
| B200 | 1 | not measured | -- | -- |

Two separate findings sit in that table, and the second matters more.

**B200 is 1.83x faster than H200 at four GPUs.** Not the 2.3x the ratio of peak
FLOPS suggests: the model fills the bigger card proportionally *less*, roughly 7%
MFU against the H200's 8.7%. Measure, do not extrapolate from spec sheets.

**One GPU beats four, on the same hardware.** The 1-GPU H200 figure is from a real
run in progress, not a benchmark: 2.30 s/step against 2.54 for four cards. FSDP
shards every layer, so each rank all-gathers parameters on every microstep, and
splitting a 131,072-token batch across 4 ranks leaves only 2 gradient-accumulation
microsteps per rank for that traffic to amortise against. Four cards are therefore
slower in wall-clock *and* 4.4x more expensive in GPU-hours. `gpus: 1` in the 1B
configs is a throughput decision, not a courtesy to other users.

The B200 measurement above is a 4-GPU number, so it is not the configuration you
would actually run. A 1-GPU B200 run has not been measured and is the obvious next
thing to time.

Startup and compile took about 11 minutes of the 12:58 total. One-time, but it
dominates any run short enough to be called a smoke test.

## You cannot resume a torch 2.6 run here. This is the important part.

A run started under `lment` cannot be continued under `lment-b200`. Both twins
were moved to B200 mid-run and both died within a minute:

    RuntimeError: Missing key in checkpoint state_dict:
                  optim.param_groups.0.decoupled_weight_decay

AdamW's `param_groups` gained `decoupled_weight_decay` between torch 2.6 and
2.11, so optimizer state written by the old stack lacks a key the new one
requires. The weights are fine; the optimizer state is not. No configuration
reaches this.

The two constraints are mutually exclusive and worth stating plainly:

- B200 needs torch >= 2.7 with CUDA 12.8+, because 2.6+cu124 has no `sm_100`
  kernels;
- a checkpoint written by torch 2.6 can only be resumed by torch 2.6.

**So B200 is available only to runs started from scratch under this environment.**
An in-flight experiment stays on the hardware it began on. Note also that the
resume *matched* -- the log printed `resuming from ...` -- because config matching
succeeds long before the state dict is read. `resuming from` in the log is not
evidence that a resume worked; wait for a step counter.

## Pin the Elasticsearch client below 9

The environment resolves `elasticsearch` to 9.x, which sends
`compatible-with=9` headers. The deployed server is 8.13.4 and rejects them:

    elasticsearch.BadRequestError(400, 'media_type_header_exception',
      'Accept version must be either version 8 or 7, but found ...')

    pip install "elasticsearch>=8,<9"

This only bites on an *ablated* run. A control has `blacklist: null` and never
queries the index, so it submits happily while its twin fails -- which is exactly
how it presented: one job submitted, the other did not.

## What is still untested

The 50-step run trained from random init with the downstream evaluator disabled:

- **The downstream evaluator and the `olmes` path.** `transformers` went 4.56 to
  5.15, a major version, and none of that code ran here.
- **Anything beyond 50 steps.** Long-run stability, checkpoint cadence under load
  and preemption/requeue were not exercised.

Imports are clean: `olmo_core`, `TransformerConfig` and `examples.kas.train` all
load under the new stack.
